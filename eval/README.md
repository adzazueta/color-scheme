# Evaluation

Run `vp run eval` on the maintainer's machine. It builds the package, evaluates both private cover sets with both `tonal` and `fidelity`, and benchmarks both variants. No service or listening port is needed. Node type declarations are a development dependency for this tooling; `tsconfig.src.json` excludes ambient type packages so the package itself stays free of Node and DOM types.

The covers are read from `../color-extractor-eval` next to the main checkout, including when this command runs in a linked worktree. `COLOR_EXTRACTOR_EVAL_DIR` overrides that folder. The original images are read only and never copied, converted, or re-saved.

Cover ids come from the SHA-256-to-id mapping in color-extractor's public `eval/annotations/{dev,test}.json`, read from the sibling `../color-extractor/eval/annotations` of the cover repository. Set `COLOR_EXTRACTOR_ANNOTATIONS_DIR` to override that annotation folder. Every cover must have a unique mapped id and every annotation must have its cover. Unknown, missing, duplicate, or cross-set covers fail the run. Renaming an image preserves its id.

Extraction uses `@adzazueta/color-extractor/node` 0.4.0, `mode: "perceptual"`, `count: 5`, and default decoder limits. This matches color-extractor's evaluation configuration and decoder, with sharp 0.35.5. Each cover is decoded and extracted once, then passes through `seedsFromColorExtractor` and `createColorScheme(seeds, { variant })` for each variant. Public reports record extractor and decoder versions and the annotation file hash.

`eval/reports/3/tonal/` and `eval/reports/3/fidelity/` each contain `dev.json`, `dev.md`, `test.json`, and `test.md`; `eval/reports/3/bench.md` records both variants together. The algorithm version comes from each generated scheme. Report schema version 2 retains accent placement counts and per-cover placement and adds the variant to its header. Historical `eval/reports/1/` and `eval/reports/2/` stay unchanged. Reports contain cover ids, extracted hex colors and coverage, seeds and their sources, all roles, all given-seed adjustments, and verification results. They contain no private image names, paths, or image data. Color.js independently verifies the final 8-bit colors against every reported guaranteed contrast and Oklab lightness minimum. A verification failure writes the diagnostic reports and exits unsuccessfully.

Tonal is algorithm 3's default: accents start at tones 40/80, keep seed hue with chroma capped at 0.16/0.10, and use built container lightness. Given accent seeds are always reported on their accent role. Fidelity preserves algorithm 2's construction and reports, apart from the algorithm 3 metadata. The evaluator explicitly compares fidelity's roles, seeds and exact report numbers with `eval/reports/2/` on all 84 covers and fails if any differ. Reports reject mixed variants as well as mixed versions. Both variants share surfaces, status colors, seed derivation, adapter behavior and guarantees.

Fidelity summarizes **given seeds only**: exact appearances and average absolute `lightnessShift` from `ModeReport.adjustments`, per seed and mode, with an explicit given-cover denominator. Derived seeds are recorded and counted separately because they are not colors extracted from the cover. A seed with no observations has a null mean (`n/a` in Markdown). Lightness shift does not measure chroma changes.

Placement summarizes **all accent seeds**, separately for `primary` and `secondary`, light and dark mode, and `given` and `derived` sources. A seed is `exactX` when its hex equals the accent, `exactContainer` when it equals only the container, and `moved` otherwise. Each seed belongs to exactly one case (accent wins if both match). JSON records `covers[].placement[seed][mode]` and `summary.placement[seed][mode][source]` with `total`, `exactX`, `exactContainer`, and `moved` counts, including zero-count groups. Markdown and the HTML header show the same table, and each HTML cover marks both seeds' placement in each mode. Fidelity can stay unchanged when a seed moves from an exact accent to an exact container; placement makes that change visible.

Open `eval/out/dev-tonal.html`, `eval/out/test-tonal.html`, `eval/out/dev-fidelity.html`, and `eval/out/test-fidelity.html` locally for visual review. These ignored pages embed their CSS and reference the original covers through local file URLs; they need no external network resources. Each cover shows its extracted colors, seeds, 34 roles and sample interfaces in both modes, and adjustments. Their content and order are deterministic for the same inputs. Public reports include run provenance; timestamps and benchmark measurements naturally vary between runs. Maintainer approval of the visual result remains a release requirement before 0.1.0.

The benchmark uses `bench/create.bench.ts` and the same `bench/seeds.ts` inputs for each variant against `dist/index.js`, with 500 ms of measurement and 100 ms of warmup per case. Each benchmark records its variant in both its label and reporter metadata. The whole-set result is normalized to one scheme, following CI's JSON reporter processing. `bench.md` records per-seed measurements, CPU, cores, memory, OS, architecture, and Node version. Extraction and decoding are outside this timing: the target is below 5 ms to generate a complete light-and-dark scheme for each variant and each case. The local evaluation exits unsuccessfully if any mean reaches that target; CI benchmark execution itself continues to report timings without a machine-dependent limit.

This follows color-extractor's sorted hash-based inventory, public JSON/Markdown, versioned report folders, local benchmarks, and Vite TypeScript runner. It evaluates only perceptual extraction because this package evaluates scheme fidelity, rather than comparing extractor ranking modes or matching human annotations. It uses annotations only for ids, requires a complete inventory, and never writes results into the private cover repository. It has no extractor threshold calibration, lab, or clean-commit gate: evaluation does not tune an extractor, and reports must be generated alongside the implementation before committing this task.
